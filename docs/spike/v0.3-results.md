# v0.3 Scale Spike: results

The v0.3 spike measured whether the techniques chosen for 80,000 units fit the performance budget. The [plan](../superpowers/plans/2026-10-05-v0.3-scale-spike.md) has the method. This page has the numbers, the go/no-go decision for each row, and the answers v0.4 needs.

The spike code is on the `spike/v0.3` branch, tagged `v0.3-spike`, and is never merged. The raw CSVs behind every number are in [`docs/spike/v0.3/`](v0.3/).

## Summary

Every row has been measured. **Three rows are go as specified and one is go with a fallback. For the other three, the fallback ladder didn't reach the budget, and the owner decided on 2026-10-08:** raise the bandwidth budget, schedule flow-field rebuilds asynchronously, and adopt the async tick with the host-tick gap fixed in v0.4.

## Decisions taken before measuring

Agreed with the owner on 2026-10-05 (plan, Task 0).

- **D1. Map size: 512 × 512 and 1024 × 1024, both measured.** At 30 % rock, 512² has about 183,000 walkable tiles. 80,000 units cover about 22 % of that at 512², but only about 5 % at 1024². So 512² is the stress size and 1024² is the realistic one. v0.4 picks the shipped size from these results.
- **D2. Continuous positions, shared tiles, separation steering, mixed unit sizes.** 90 % of units are small (radius 0.35 tiles) and 10 % large (radius 0.7). Large units path on clearance-filtered flow fields. One-unit-per-tile `TileOccupancy` is retired in v0.4.
- **D3. The 25 ms tick budget is split 14 / 5 / 2 / 4 ms:** simulation, fog, flow fields, replication encoding.
- **D4. Defaults with extreme vision ranges.** The reference load and battle layout are as the plan sets them. Unit vision is swept from 6 to 32 and building vision from 10 to 20. The go/no-go uses vision 8, and each row also reports the largest radius that fits.
- **D5. Wire-byte capture with `sudo tcpdump` was allowed.** It wasn't used: the soak counts the bytes received at each raw KCP client instead (see the bandwidth row).

## Simulation tick

Burst `ISystem`s in a 20 Hz group: gather, spatial hash, combat, movement with separation, and lifecycle (20 deaths and 20 spawns a tick). Movement with separation is about 80 % of the tick.

**Battle layout, 80k units** (3 runs each, `sim-battle.csv`):

| Configuration | 512² p95 | 1024² p95 | Stuck share at peak (p95) |
|---|---|---|---|
| Default (target search every 4 ticks, separation every tick) | 21.9 ms | 16.4 ms | 0.44 |
| 1: target search every 8 ticks | 21.7 ms | 15.0 ms | 0.29 |
| 2: + separation every 2 ticks | **14.3 ms** | **9.9 ms** | 0.33 |
| 3: + movement in halves | **11.5 ms** | **9.1 ms** | 0.14 |
| Clump stress (every army to the centre), fallback 2 | 14.4 ms | 17.2 ms | 0.16 |

**Scaling** (armies marching from their HQs, ~10 % engaged, `sim-scaling.csv`): 10k / 20k / 40k / 80k units take 1.1 / 2.3 / 5.6 / 14.6 ms on 512², and 1.0 / 2.1 / 4.8 / 12.9 ms on 1024².

**Async tick.** When the tick only schedules its jobs and completes them at the next tick boundary, with the host free in between, the main thread spends **0.2–0.7 ms** a tick (boundary wait ≤ 0.5 ms p95). The simulation fits on the worker threads.

**Unit quality.** About 82–85 % of units overlap another unit in this layout, and up to 44 % make no progress for 2 s at the peak of a fight. Separation is a soft constraint, as D2 expected. Fallback 3 reduces the stuck share at the peak to 14 %.

**Decision: go with fallback 2 on 1024² (9.9 ms). 512² needs fallback 3 (11.5 ms).**

## Flow fields

| Design | Tick p95 (512² / 1024²) | Order latency p95 | Memory |
|---|---|---|---|
| Full fields, lazy rebuild (fallback 1) | 6.7 / 26.6 ms | 350 ms | 96 / 384 MB |
| Hierarchical 32×32 sectors, 2×2-tile cells (fallbacks 2 + 3), ≤ 2 rebuilds a tick | 2.7 / 7.0 ms (mean 1.0 / 1.9) | 50 ms | 0.7 / 0.9 MB |
| The same, ≤ 1 rebuild a tick | 0.7 / 1.7 ms | **1,950 ms**, and ~178 orders never served | 0.4 / 0.6 MB |

The cost is spiky: the mean is within budget, but a terrain change that re-routes many fields lands in one tick. Fallback 4 (an LRU cap on live fields) only cuts memory, which already passes, so it wasn't run.

**Decision (owner, 2026-10-08): async rebuilds.** Keep the hierarchical design with ≤ 2 rebuilds a tick, but schedule the rebuilds asynchronously, completing them at the next tick boundary like the simulation. Then the 7 ms lands on worker threads, not the main thread. The alternative is to accept the overrun.

## Spatial hash

Counting sort into a uniform grid, rebuilt every tick (0.3 ms). Nearest-enemy search is sliced so each unit searches every 4 ticks. Battle layout, 80k units, at the peak of the fight (`hash.csv`):

| Cell size | Slice p95 (512² / 1024²) | Clump p95 |
|---|---|---|
| 4 | 3.7 / 3.7 ms | 18.1 ms |
| **5** | **2.35 / 2.35 ms** | **10.4 ms** |
| 8 | 4.6 / 4.6 ms | 24.7 ms |

The `NativeParallelMultiHashMap` variant builds in about 0.6 ms against the counting sort's 0.3 ms. Brute force takes about 970 ms. **Decision: go, cell size 5.**

## Bandwidth

**Stage A** counts the encoded bytes exactly for each of 8 clients over the scripted 60-second match, then adds Mirror batching, KCP segment and UDP/IP overhead. It uses the full simulation and fog, orders every 2 s, 20 spawns and 20 deaths a tick, and 4 terrain changes a second.

**The plan's model is 5–15× over budget.** Corrections are about 90 % of the bytes. The prediction error before correction is a median **0.9 tiles** within 0.2 s, for two reasons:

1. After a correction, the client steered toward the waypoint *after the leg the prediction had reached*. That can be behind the unit, or around a corner.
2. The client always predicted full speed, but units stop to fight and slow down in crowds.

Two encoder changes fix most of this. Corrections now resume at the waypoint after the route segment nearest the unit (`-cproj`), and carry its measured speed in one byte (`-cspeed`). The median error falls to 0.3 tiles. The rest is crowd jostle from separation.

**The ladder** (FFA / 4v4, 512², payload KB/s per client, single exploration runs, `bandwidth-exploration.csv`):

| Step | FFA | 4v4 | In-view error p95 |
|---|---|---|---|
| Plan's model | 653 | 1,863 | 0.19 tiles |
| 1: corrections at 5 Hz | 380 | 1,019 | 0.16 |
| 2: + 1/8-tile deltas against the prediction | 280 | 708 | 0.16 |
| + **view tier** (not on the ladder): fine corrections only inside the client's 64×36-tile camera; off-screen units checked at 1 Hz against a 2-tile threshold | 194 | 277 | 0.16 (off-screen 0.8–1.4) |
| + a hard 110 KB/s byte budget, largest error first | 97 | 95 | **29–32 (unusable)** |

Step 3 (group orders sent once with a shared route) can save at most the MoveOrder share (12–30 %) of a stream that is mostly corrections, so it can't close the gap. Step 4 (dedicated servers) doesn't change what each client receives.

**The chosen configuration** is steps 1 and 2, plus the view tier, speed and projected resume (`-corri 4 -cq 8 -cproj -cspeed -view 64`). 3 runs each, `bandwidth.csv`. Mean per client, wire bytes in brackets:

| | FFA 512² | FFA 1024² | 4v4 512² | 4v4 1024² |
|---|---|---|---|---|
| Average, vision 8 | 202 (218) KB/s | 193 (208) | 263 (284) | 277 (297) |
| Peak 1 s, vision 8 | 305 | 387 | 513 | 706 |
| Average, vision 32 | 274 | 263 | 264 | 278 |
| Encode, 8 clients (Burst, parallel) | 1.8 ms mean, 2.4 p95 | 1.8 / 2.2 | 3.6 / 4.8 | 3.6 / 4.6 |
| Interest-set build (main thread) | 4.9 ms | 5.0 ms | 2.3 ms | 2.3 ms |
| Match-start snapshot at 256 KB/s | 1.6 s | 2.0 s | 3.3 s | 4.0 s |

The client sees an in-view prediction error of 0.20 tiles p95, and 1.6–1.8 tiles for off-screen units, which is enough for the minimap.

**Stage B (soak)** pushes the same streams through the project's `KcpTransport` (MTU 1,200, windows 4,096) to 7 raw KCP clients on loopback, paced at 20 Hz in real time (`soak.csv`). The transport carries the streams:
- latency p95 is 0.8 ms (FFA) / 1.3 ms (4v4)
- send queues drain (1–3 segments at the end against 7–13 at the start)
- every reliable byte arrives
- clients receive 189 / 286 KB/s

`tcpdump` wasn't needed, because the clients count the bytes they receive.

**Decision (owner, 2026-10-08): raise the budget to 256 KB/s average and 768 KB/s peak, keep 10,000 units per player, and recommend dedicated servers for full 8-player matches.** At ~200 KB/s (FFA) to ~280 KB/s (4v4) average, the chosen configuration is 1.5–2.2× the 128 KB/s budget, and its peaks are up to 2.8× the 256 KB/s peak budget. The options:
- **Raise the budget** to about 256 KB/s average and 768 KB/s peak (2 / 6 Mbit/s per client). The host's upload for 7 remote clients would then be about 11–16 Mbit/s, against the spec's 7 Mbit/s estimate.
- **Lower the scale**, for example to 5,000 units per player.
- **Dedicated servers** for 8-player matches, which fixes host upload but not client download.

The encoder itself is within its 4 ms budget, but the interest build adds 2–5 ms on the main thread and needs the same Burst treatment in v0.5.

## Combined host

One windowed player hosts and plays. It runs:
- the 20 Hz server: simulation, fog slice, terrain changes with flow rebuilds, route maintenance, interest sets, and encoding for 8 clients, 7 of them raw KCP clients on loopback
- the local client: interpolation and instanced drawing of its own army plus the visible enemies, 12k units in FFA and 40k in 4v4

The chosen bandwidth configuration is used throughout (`combined.csv`, 3 runs each):

| Mode | Tick main p95 (p50) | FPS mean | Frame p99 | Late ticks |
|---|---|---|---|---|
| Sync, FFA | 42.7 ms (31.9) | 2,590 | 33.8 ms | 0 |
| Sync, 4v4 | 44.3 ms (32.7) | 1,410 | 37.7 ms | 3 |
| Async, FFA | 26.4 ms (10.9) | 2,290 | 14.1 ms | 0 |
| Async, 4v4 | 25.6 ms (11.8) | 1,190 | 18.0 ms | 0 |
| Async with sim fallback 2, FFA / 4v4 | 26.6 / 25.1 ms (11.1 / 11.8) | 2,250 / 1,210 | 13.7 / 17.7 ms | 0 |

Async is the only workable mode: the simulation's jobs run during the frames between ticks, and the boundary waits less than 1 ms. What remains on the main thread spikes on terrain-change ticks:
- the synchronous flow rebuilds and field refresh
- the fog slice (2.7–4 ms)
- the interest build (2–5 ms)
- route maintenance

**Decision (owner, 2026-10-08): adopt the async tick and fix the gap in v0.4**, which gates on a 25 ms p95 host tick. The host misses by about 1.5 ms at p95, and frame rate passes easily. The recommendation is to adopt the async tick and move flow rebuilds, fog and the interest build onto jobs that complete at the next tick boundary. All three already run as Burst jobs in the spike except the interest build. That should leave a large margin, but it is an expectation, not a measurement.

## Answers to v0.4's open decisions

| Decision | Answer |
|---|---|
| Target-search slice interval | 8 ticks |
| Separation | Strength k = 1, one pass, every 2 ticks. Add movement in halves if the map is 512² |
| Spatial-hash cell size | 5 tiles |
| Flow-field design | Hierarchical, 32×32-tile sectors with 2×2-tile cells, lazy rebuild, ≤ 2 rebuilds a tick, scheduled asynchronously. No live-field cap needed: memory is < 2 MB |
| Sync or async tick | **Async**. Jobs complete at the next tick boundary, and clients see one extra tick (50 ms) of latency |
| Buildings and walls | Instanced, like units |
| Fog | 5 Hz, 1×1-tile grid, unit vision 8 (at most 12), building vision up to 20 |
| Map size | **1024²**. The simulation passes there at fallback 2, while 512² needs fallback 3 and is too crowded to play (82–85 % overlap, 44 % stuck at a fight's peak) |
| Unit size classes | Separation alone leaves heavy overlap in battle-density crowds. The large class's clearance-filtered field doubles the field count but costs < 1 MB with sectors. v0.4 needs stronger, damped separation, and should measure stuck share as a quality gate |

## Gaps for later versions

- **v0.4 needs a large map**, generated or authored, at least 1024². `Map_2` holds about 3,000 tiles.
- **One-unit-per-tile `TileOccupancy` is replaced by separation** with continuous positions.
- **The 20 Hz fixed-step group replaces the 50 Hz `FixedUpdate` cadence**, run async.
- **The match-start snapshot needs chunking.** It is 1.6–4.0 s at 256 KB/s, larger than one reliable message.
- **The interest-set build needs to be a Burst job** (2–5 ms on the main thread today).
- **Terrain changes must not rebuild flow fields synchronously** on the host's main thread.
- **v0.5's movement protocol should adopt** the camera view tier, speed-carrying corrections, the projected resume waypoint, and delta-coded corrections. Routes are re-traced from the unit's current tile and nearly every re-trace counts as a change. A production server should compare from the route's own start (see the spike's `ReplicationMatch.ApplyTerrain` note).
- **Separation quality** (overlap and stuck share) needs work before 10k-unit fights look right.

# v0.11 New Ground: Design

**Status:** scope agreed with the owner on 2026-10-16 (brainstorm); written for the owner's review. Not started; the implementation plan is written when v0.11 starts (after v0.10, whose overlays and control API it uses).
**Parent:** [roadmap](../../roadmap.md) §2 v0.11.

## 1. Goal

1. Replace the cave generator (45 % noise smoothed into caves, eight clearings on a circle, straight corridors, sprinkled gems) with a **region-graph generator**: open regions joined by planned lanes and chokepoints, with contested resource expansions. This closes the owner's design request "map generation looks boring" in [known-issues.md](../../known-issues.md).
2. Replace the public lobby clearing claim with **private start points**: the server deals each player their own options, which nobody else learns, and the player picks one by placing their HQ.

**Agreed with the owner (2026-10-16):** procedural from the seed; chokepoints, lanes and expansions; no symmetry and no new terrain types; options dealt privately, count set by the host, picked during *PlacingHQ*; teammates see each other's options and picks. **The pick time is a host setting** from 0 (no picking: everyone gets a random one of their options) to unlimited (the match waits until everyone has picked).

**Out of scope:** new tile types (water, forest), hand-authored maps, archetype pickers, symmetric layouts, team-aware dealing.

## 2. The generator

`World/RegionMapGenerator.cs` replaces `MapGenerator` behind the same entry point (`MapStore.Generate(size, seed, gemChance)`), so the server, every client, the lobby preview and the menu battle all use it. Same seed and size give the same tiles on every machine; the existing `MapHash` check stays. Randomness is `Unity.Mathematics.Random` from the seed (integer-based); geometry that decides tiles uses integer or exactly reproducible arithmetic, so Linux and Windows clients agree.

### 2.1 Steps

1. **Regions.** Poisson-disc placement (seeded) of region centres inside the border, by kind:
   - **Start sites**: radius 12 (fits the 5×5 HQ and a base around it, as `HqClearRadius` today). Count by map size (§2.3).
   - **Expansions**: radius 16–22, each with a rich gem field.
   - **Central areas**: a few large open regions (radius 24–40), the battlefields between bases.
2. **Graph.** Delaunay-triangulate the centres (its edges never cross), take the minimum spanning tree so everything connects, then add back about a third of the remaining shortest edges so there are loops and more than one route between bases. Every start site gets degree ≥ 2, so one wall can't seal it.
3. **Lanes.** Each graph edge becomes a lane: a thick polyline through one or two jittered midpoints, width 6–10 tiles. About 40 % of edges (`<Map><ChokepointShare>`) get a **chokepoint**: a section 3–6 tiles wide and 8–20 long. A large unit needs 2 tiles of clearance (`FlowSizeClass.MinClearance`), so a 3-wide choke passes Heavies in single file and walls can close it.
4. **Carve and dress.** Rasterise regions and lanes into a floor mask, roughen the edges with seeded value noise and one smoothing pass, so it reads as rock rather than geometry. Everything else is rock; the border ring last.
5. **Gems.** Expansions get rich fields (clusters of 20–40 gem tiles on the region's rim, facing floor). Each start site gets one guaranteed vein (6–10 tiles) on its rim, away from its lanes. Scattered gems elsewhere drop to a low `GemChance`.
6. **Fairness tests** for every start site:
   - open floor within its radius ≥ a set area;
   - its vein exists and faces floor;
   - path distance (BFS over floor) to its nearest other start site lies within `[MinStartDistance, MaxStartDistance]`, scaled by map size;
   - distance to the nearest expansion within a band, so no site is far from contested resources;
   - every region is reachable from every other.

   A seed whose layout fails is retried with derived sub-seeds (up to 32); if all fail, the best-scoring attempt is used, so generation never fails. The retry count is deterministic, so clients reach the same map.
7. **Output:** tiles, `StartSites` (centres), `Expansions`, and the region graph (for the v0.10 overlay's Regions layer and for tests).

### 2.2 Budget

Every client regenerates the map, and the lobby preview generates it on every seed change, so the 1024² map must generate in **≤ 1 s** on the reference machine (today: about 170 ms). Carving, noise and BFS run as Burst jobs; the graph work is small.

### 2.3 Numbers (in `GameConfig.xml`, `<Match><Map>`)

| Map size | Start sites | Expansions | Central areas |
| --- | --- | --- | --- |
| 256 | 16 | 4 | 1 |
| 512 | 28 | 8 | 2 |
| 1024 | 40 | 14 | 4 |

Plus `ChokepointShare`, `LaneWidth` (min, max), `ChokeWidth` (min, max), `MinStartDistance`, `MaxStartDistance`, `ExpansionGemTiles`. These are starting values to tune in play.

## 3. Private start points

### 3.1 Rules

- **Lobby.** `MatchSettings` gains `StartOptions` (1–4, default 3) and `StartPickSeconds` (§3.1a), set by the host like the other settings. `MatchSettingsRules.IsValid` checks the range; `LobbyRules.CanStart` also requires `players × StartOptions + Spare ≤ StartSites` for the chosen map size (`Spare` = 2, so one unused site always remains and an enemy's position is never pinned down by elimination), and the lobby greys out values that wouldn't fit.
- **Removed:** `ClientPlayer.startSite` (a public SyncVar today, so every client knows every claim), `GameCore.Cmd_SetStartSite`, `LobbyRules.AssignStartSites` / `IsStartSiteChoiceValid`, and the lobby preview's clickable markers. The lobby preview still shows the terrain, with no start points on it.
- **Dealing.** When the match scene loads and the server has generated the map (`WorldStateManager.OnStartServer`), `StartDeal.Deal(siteCount, owners, options, rng)` gives every player (bots included) `StartOptions` distinct sites, unique across players, uniformly at random. **The randomness is server-only** (`System.Security.Cryptography.RandomNumberGenerator`), never the map seed: every client can regenerate the map and would otherwise compute everyone's deal.
- **Storage.** `ServerPlayer.StartOptions` (site indices) and `ServerPlayer.StartPick`, server only.
- **Delivery.** `ClientPlayer.TargetStartOptions(conn, own, teammates)`: the player's own site indices, plus, in Teams mode, each teammate's options and pick. When a player places their HQ, their teammates get `TargetTeammatePick`. Nothing goes to anyone else.
- **Picking.** Each player's options are ringed and numbered on the map (`ClearingRing`), and the camera starts on the first. The player places the HQ inside any option; that fixes their pick. How long they have depends on the host's setting (§3.1a).
- **Random placement.** Whenever the server places an HQ for a player (pick time 0, or the time ran out), it picks one of that player's options with server randomness and places the HQ at the site's centre, searching outward within the site for a free footprint. Then the countdown starts as today, once every HQ is down.

### 3.1a Pick time (host setting)

`MatchSettings.StartPickSeconds`, chosen by the host in the lobby from `<Lobby><StartPickSeconds>` in `GameConfig.xml` (proposed `0 15 30 45 60 90`, default 45) plus **Unlimited**:

| Setting | *PlacingHQ* |
| --- | --- |
| **0: Random** | No picking. The server places every player's HQ at a random one of their options as soon as the match scene loads, and the countdown starts. Players still receive their own options (they need to know where they are), but nothing to choose. |
| **15–90 s** | `GameCore.HqPlacementEndTime` (a SyncVar, like `CountdownEndTime`) is set that far ahead; the HUD shows the timer. At the deadline the server places a random option for everyone who hasn't placed. |
| **Unlimited** | No deadline: the match waits until every player has placed. `HqPlacementEndTime` is 0 and the HUD shows "Waiting for N players" instead of a timer. A player who leaves is removed as today, so a disconnect can't stall it. |

- Stored as an int: `0` random, `> 0` seconds, `StartPickRules.Unlimited` (`-1`) for unlimited. `MatchSettingsRules.IsValid` accepts only `0`, a value from the config list, or `Unlimited`, so a modified client can't set other values.
- The setting is public lobby information, like the map size, so it reveals nothing about the deal.
- **Unlimited means unlimited** (owner, 2026-10-16): there is no host override. An idle player holds everyone in *PlacingHQ* until they place or leave; a host who doesn't want that picks a timed setting.
- **Validation.** `WorldStateManager.CheckPlacement` refuses an HQ unless every footprint tile is inside one of the sender's options (`PlacementResult.OutsideStartOptions`). This check runs **before** the footprint-free check, so probing `CanBuildBuildingCommand` at another player's site always answers "outside your options" and never "occupied", which would reveal an enemy HQ.

### 3.2 What players can learn

| Who | Learns |
| --- | --- |
| The player | Their own options; their own pick |
| A teammate (Teams mode) | That player's options and pick |
| Anyone else | Nothing about either. Every start site is plain open ground in the map they regenerate, so they know where bases *might* be, never which. |

An HQ is a building, so it reaches enemies only through fog, like any other building.

### 3.3 Dev and perf

Bots are dealt like players; `PerfMatch` and `QaSmoke` place their HQs at their dealt options (perf runs deal deterministically from `-perf`'s fixed seed, so the gate's layout is stable). The perf gate's fronts battle is laid out from the dealt sites instead of the old circle.

## 4. UI (Figma first)

- Lobby: **Options per player** and **Pick time** (Random, 15 s … 90 s, Unlimited) settings (host), the preview without markers.
- HUD during *PlacingHQ*: numbered option rings, a "Pick your start: 0:38" timer (or "Waiting for N players" when Unlimited) in the placement overlay, and the teammates' options in their colour.

None of it is built before the owner approves the frames.

## 5. Testing

- **EditMode, generator:** same seed and size → same hash (and a recorded hash per size, so an accidental change shows); 200 seeds × 3 sizes per run meet every fairness test, plus a 1,000-seed manual run before release; border never dug; every region connected; every start site degree ≥ 2; chokepoint widths within bounds for both size classes; generation time at 1024² under budget.
- **EditMode, dealing:** options distinct and unique across players; counts; the deal doesn't depend on the seed (two deals with the same seed differ); `CanStart` with too many options.
- **LeakTests:** no message to a player carries another non-teammate's options or pick; `startSite` no longer exists as a SyncVar; the placement answer never reveals an occupied site outside one's options.
- **PlacementRulesTests:** HQ inside and outside options; random placement finds a free footprint in the site.
- **Pick time:** `IsValid` accepts 0, the config values and Unlimited and refuses anything else (fuzzed); 0 places every HQ at load; a timed pick places the rest at the deadline; Unlimited never places for a player and starts the countdown only when the last one places or leaves.
- **PlayMode:** a hosted 2-player match with a timed pick where one player picks and the other times out; one with pick time 0; Teams mode where teammates see each other's options.
- **Performance:** the perf gate on the new layout.

## 7. Open decisions (defaults used until the owner says otherwise)

1. **Site, expansion and central-area counts** per map size (table §2.3).
2. **Options range:** 1–4, default 3.
3. ~~Pick time~~ **Decided (owner, 2026-10-16):** a host setting from 0 (random) to Unlimited. No "place the rest randomly" button in Unlimited mode (owner). Still open: the list of timed values (proposed 0, 15, 30, 45, 60, 90; default 45).
4. **Spare sites:** 2 beyond what is dealt.
5. **Teammate dealing:** random, so teammates may start far apart. Team-grouped dealing was not chosen; it could be a lobby option later.
6. **Expansions as bases:** an HQ may only go in a dealt option, never in an expansion.

# v0.10 Insight: Design

**Status:** scope agreed with the owner on 2026-10-16 (brainstorm); written for the owner's review. Not started.
**Parent:** [roadmap](../../roadmap.md) §2 v0.10. **Plan:** [2026-10-16-v0.10-insight.md](../plans/2026-10-16-v0.10-insight.md).

## 1. Goal

Make the running game observable and drivable, by Claude and by the owner, and let players watch a match back:

1. a **control API** with a **CLI** (`tools/war2d`), so Claude can host, join, set up a scenario, step it, read its state and take screenshots without the owner at the keyboard;
2. **debug overlays** that draw what the pathing, combat, fog and replication systems are doing;
3. **structured logs** (`WarLog`) with categories, levels, a ring buffer and a per-session file;
4. **match recordings** that every player can watch after the match, with no fog.

**Agreed with the owner (2026-10-16):** API in the editor and development builds only; scenario commands in the API and the TIM console, with no in-game debug panel; the host records and sends each player the file after the match; a Replays screen in the main menu.

**Out of scope:** an in-game cheat panel, remote (non-localhost) access, release-build access, replaying by re-simulation, live spectating of a running match.

## 2. Control API

### 2.1 Reach and safety

- `DebugApi.Allowed` is true only when `DevUi.Enabled` (editor or development build) **and** the process is the editor in play mode or was started with `-debugApi [port]`. Release builds never open it, whatever the command line says.
- It listens on **127.0.0.1 only**, default port **7790** (`-debugApi 7791` picks another).
- On start it writes `<persistentDataPath>/debugapi/<port>.json` with `{port, pid, token, role}`; every request must carry that token, so another local user's process can't drive it. The file is deleted on quit. `tools/war2d list` reads this folder.
- Each API command runs with the dev APIs allowed (bots, free spawns and buildings, as with `-perf`) for the duration of that command only (`DevApi.Scope()`). Keeping them on whenever the API listens would change the rules of every editor match and PlayMode test, since the API is on in every editor play session. A log line says the API is listening.

### 2.2 Protocol

JSON lines over TCP, one request per line:

```json
{"id": 7, "token": "…", "cmd": "units", "args": {"owner": 2, "type": "Tank", "box": [0, 0, 64, 64], "limit": 200}}
{"id": 7, "ok": true, "result": {"count": 133, "units": [{"id": 1048577, "owner": 2, "type": "Tank", "pos": [12.4, 30.1], "health": 100, "stance": "Idle", "target": -1}]}}
```

- A background thread accepts connections and reads lines; requests go onto a `ConcurrentQueue` and run on the **main thread** in `Update`. Nothing runs off the main thread except the socket I/O.
- Commands that change the world queue a `SimCommand` or call the existing server path (`DevSpawnUnit`, `DevPlaceBuilding`, `GameCore.AddBot`, the order commands' internals). The tick rules in `CLAUDE.md` still hold: no command touches `Unit` entities or `SimData` between ticks; readers use the last settled snapshot.
- Long commands (`step`, `wait`) answer when done, with a timeout.
- Errors are `{"ok": false, "error": "…"}`. Unknown commands, bad arguments and wrong roles (a server command sent to a pure client) are errors, never exceptions out of the loop.

### 2.3 Commands (first set)

| Group    | Commands                                                                                                                                                                                                                                                                                                                    |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ | --------- | ---------------------------------------------------- |
| Session  | `ping`, `info` (role, version, scene, game state, tick, ports), `host [settings]`, `join <route>`, `leave`, `start [settings]`, `quit`                                                                                                                                                                                      |
| Read     | `state`, `players` (resources, state, team, colour), `units` (filters: owner, type, box, stance; limit), `unit <id>`, `buildings` (filters), `tiles <box>` (ASCII or array), `fog <owner> <box>`, `orders` (live orders and followers), `perf` (last tick timings, replication bytes), `log` (tail, category, level, since) |
| Scenario | `bots add <n>`, `spawn <owner> <type> <tile> [count]`, `build <owner> <type> <tile> [rot]`, `resources <owner> <amount>`, `order <owner> <ids                                                                                                                                                                               | box> <kind> <goal> [queue]`, `diplomacy <a> <b> attack | vision on | off`, `kill <id>`, `pause`, `resume`, `step <ticks>` |
| View     | `camera <x> <y> [zoom]`, `select <ids>`, `screenshot [path]` (returns the PNG path), `overlay <layer> on                                                                                                                                                                                                                    | off [arg]`                                             |
| Wait     | `wait state <GameState>`, `wait ticks <n>`, `wait units <owner> <count>`                                                                                                                                                                                                                                                    |
| Replays  | `record status`, `replay open <file>`, `replay seek <seconds>`, `replay speed <x>`                                                                                                                                                                                                                                          |

Read commands on a client answer only from what that client holds (`ClientWorld`, `ClientBuildings`, its own fog); server-only reads (`orders`, other owners' fog) need the host process. That keeps the API from becoming a way to test leaks by accident: a client process reports what the client really knows.

**Pause and step.** `SimContext` gains `Paused` and a step budget. `SimBoundarySystem` settles as usual but sets `Running` false while paused and the budget is empty; `step n` adds n ticks. The building systems (`SpawnerSystem`, `ResourceSystem`, `WinLossSystem`) also skip while paused, so economy and production freeze with the units. Pause is refused outside dev (it would stop a real match for everyone).

### 2.4 CLI (`tools/war2d`)

A Python 3 script (standard library only):

- `war2d list`: running instances (port, pid, role).
- `war2d [--port N] <command> [args]`: one request, human-readable output (tables for lists, an ASCII map for `tiles`/`fog`); `--json` prints the raw result.
- `war2d shell`: an interactive prompt.
- `war2d launch --clients N`: builds nothing; starts the development build in `Builds/Dev/` as one host (port 7790) and N joiners (7791…) with `-debugApi`, `-direct`, `-noSteam` and a log file each, like `tools/qa-smoke.sh`, then waits for their API files.

A new menu item **WAR-2D → Build → Linux (Dev)** makes the development build (`BuildOptions.Development`) into `Builds/Dev/WAR-2D.x86_64`.

### 2.5 Console

The TIM console gains the scenario and overlay commands (`spawn`, `build`, `resources`, `bots`, `pause`, `step`, `overlay`, `log`), implemented by calling the same handlers as the API, in `Custom_Commands.cs`.

## 3. Debug overlays

- A `DebugOverlays` component, added in development builds only. It draws over the map and below units (a new band in `SortingOrders`).
- Layers (each off by default, toggled from the API, the console, or F1–F9 in development builds; the F keys are not in the rebinding list):

| Layer      | Shows                                                            | Source                              |
| ---------- | ---------------------------------------------------------------- | ----------------------------------- |
| Flow       | The flow-field directions of the selected units' order, per cell | server (`OrderFieldTable`)          |
| Routes     | The replicated routes of selected units                          | client (`ClientUnitStore`)          |
| Targets    | Stance colour per unit and a line to its target                  | server SoA                          |
| Fog        | One owner's fog grid (visible, explored)                         | server (any owner) or client (own)  |
| Sectors    | Sector borders, portals and the order's sector route             | server (`SectorGraph`, `OrderBook`) |
| Hash       | Units per spatial-hash cell as a heat map                        | server                              |
| Footprints | `Used` tiles and building footprints                             | server (`MapStore`)                 |
| Interest   | Which units are in one client's interest set                     | server (`InterestSets`)             |
| Terrain    | Tiles changed since the start (`ChangedSinceStart`)              | server                              |

- **Data flow.** Server layers copy only what they need in a `SimContext.Settled` handler, and only while enabled, into managed buffers; drawing happens on the main thread. With every layer off the overlay does no work.
- **Drawing.** One point-filtered texture on a quad for grid layers (a texel per tile or fog cell), and one line mesh (`MeshTopology.Lines`, rebuilt when its data changes) for arrows, target lines and borders.
- **Host only for server layers.** A joined client's overlay offers Routes and its own Fog only.
- v0.11 adds a Regions layer (the generator's graph).

## 4. Structured logs (`WarLog`)

- `WarLog.Debug/Info/Warn/Error(LogCategory, string)`. Categories: `Sim`, `Net`, `Replication`, `Steam`, `Lobby`, `Match`, `UI`, `Audio`, `Art`, `Replay`, `Dev`, `Unity` (captured).
- Each entry carries UTC time, frame, sim tick (or −1), category, level and message.
- **Sinks:** an in-memory ring (8,192 entries, thread-safe), a per-session file `<persistentDataPath>/logs/war2d-<UTC time>-<pid>.log` (last 10 kept), and Unity's own log (`Debug.Log*` with a `[Category]` prefix, so the editor console and `Player.log` still see everything).
- **Unity and Mirror logs** are captured through `Application.logMessageReceivedThreaded` into the `Unity` category (a thread-static guard stops WarLog's own forwarding from looping).
- **Levels** per category (default Info; Debug off): changed from the console or the API (`log level net debug`). Release builds keep Info and up in the file, which playtest logs benefit from.
- **Migration:** the game code's ~74 `Debug.Log*` calls and the two `TIM.Console.Log` network calls move to `WarLog` with a category. Burst jobs keep not logging.

## 5. Match recordings

### 5.1 What is recorded

- `MatchRecorder` (server only) is created by `WorldStateManager.OnStartServer` when `<Replays><Enabled>` is true. It registers a **virtual replication client** for a reserved owner id that `ReplicationService.Spectating` reports as spectating, so it gets `SimData.SeesAll`: every unit, building and terrain change, no fog. Bombs need one more exception: `SendBuildings` filters them through `BombRules.MayKnow(owner, …)`, which a spectator owner never passes, so the recorder's client is let through explicitly (and only it: eliminated players spectating mid-match still never see bombs).
- Its view box is empty, so every unit is on the **offscreen correction tier** (`OffscreenIntervalTicks`, `OffscreenThreshold`). That keeps the file small; prediction follows the routes, so movement still reads correctly, with occasional blended corrections. The owner chose this coarse tier for every recording (2026-10-16); see §8.
- Beside the replication payloads it records:
  - every death explosion and bomb blast, unfiltered (the sources `FlushDeathEvents` and `TargetPlayBlasts` use),
  - once a second, a public timeline sample per player (resources, units, buildings),
  - the match outcome and `MatchStats` at the end.
- **Header:** magic, format version, `GameVersion.Current`, map size and seed, `MatchSettings`, and the roster (owner id, nickname, colour index, team). Never Steam IDs.

### 5.2 File format

`<persistentDataPath>/Replays/<UTC time>-<seed>.war2drec`, GZip-compressed (`System.IO.Compression`):

```
header:  "W2DR" | u16 format | u32 headerLength | header JSON (UTF-8)
records: varint tickDelta | u8 channel | varint length | payload
         channel 0 unit reliable, 1 unit unreliable, 2 buildings, 3 terrain, 4 fog (first snapshot only),
                 10 explosions, 11 blasts, 12 timeline sample, 13 end (outcome + stats JSON)
```

- Payloads are copied out of the reused `NetworkWriter` buffers on the main thread and written by a background writer thread with a bounded queue; a full queue drops the recording (logged) rather than stalling the tick.
- The file is written as `.part` and renamed on finish. `<Replays><MaxMegabytes>` caps it: past the cap the recorder stops and finishes the file, which stays playable up to that point.
- Recording stops 3 s after _GameOver_ (the end-of-match wipe settles and is recorded).

### 5.3 Sending it to players

- After the file is finished and `CurrentState == GameOver`, the server sends each connected player a `ReplayOffer {id, bytes, sha256, durationSeconds}`.
- A client whose setting **Save replays** is on (default on) answers `CmdReplayWanted(id, true)`: gated by `CommandGate`, accepted only in _GameOver_ and for the current offer.
- The server then streams `ReplayChunk {id, offset, bytes}` (16 KB) on the reliable channel, paced at `<Replays><SendKilobytesPerSecond>` per client from `Update`. The client writes a `.part` file, checks length and hash, and renames it.
- Leaving, disconnecting, or the host shutting down cancels the transfer (the `.part` is deleted). The end screen shows the progress.
- **Security.** Nothing about a recording is sent before _GameOver_: `ReplayOffer` and `ReplayChunk` are refused by the sender while the match runs, and `LeakTests` gain a case. After _GameOver_ nothing in the match is secret (the same rule the end-of-match wipe and spectators already follow).

### 5.4 Watching

- **Replays** button in the main menu → a list: date, map size, players and colours, duration, file size, Watch, Delete.
- **Viewer** (`ReplayPlayer`, offline, like `MenuBattle`): regenerates the map from the header's size and seed (refusing a file whose `GameVersion` is incompatible, since the generator and codecs may differ), shows it through `MapView`, and feeds the recorded payloads to `ClientWorld`, `ClientBuildings.Current` and `ClientTerrain.Current` by tick time. It plays explosions and blasts and draws every player's colour.
- **Controls:** play and pause, speed (0.5×, 1×, 2×, 4×, 8×), a seek bar, free camera (the normal pan and zoom), a player list with each player's resources from the timeline samples, and Leave.
- **Seeking** rebuilds the client state by decoding from the start (or forward from where it is) up to the target, without drawing. If that is too slow on long matches, keyframes are a later addition (§8).
- **Malformed files** are rejected without throwing: every codec read is bounds-checked (the existing decoders already are), and the reader is fuzz-tested.
- The Replays list, viewer controls and the end screen's progress line are new UI: **Figma first**, and none of it is built before the owner approves the frames.

### 5.5 Config

```xml
<Replays>
  <Enabled>true</Enabled>
  <MaxMegabytes>512</MaxMegabytes>
  <SendKilobytesPerSecond>1024</SendKilobytesPerSecond>
  <KeepCount>50</KeepCount>   <!-- oldest replays beyond this are deleted on save -->
</Replays>
```

## 6. Testing

- **EditMode:** the API dispatcher (parse, token, unknown command, role errors) without sockets; `WarLog` ring, levels, capture guard and file rotation; overlay data capture from a `SimHarness` world; the replay codec (round trip, truncated and fuzzed files); the recorder's stream played into a fresh `ClientUnitStore` matches a live virtual spectator's store at the same tick; `ReplayOffer` refused before _GameOver_; `LeakTests` cases for the recorder client and the offer.
- **PlayMode:** an API socket smoke test in play mode (connect, `ping`, `state`, `spawn`, `step`); a hosted match that records, ends and leaves a playable file; the viewer plays a recording to the end and seeks.
- **Two-process:** `tools/war2d launch --clients 1` then a scripted session (host, join, start, spawn, order, screenshot) replaces nothing in `qa-smoke.sh` but runs beside it; the joining client receives the replay.
- **Performance:** the perf gate runs with the recorder on. The recorder is one more virtual client seeing all 80,000 units, so its encode cost and file rate are measured and reported with the gate.

## 8. Open decisions (defaults used until the owner says otherwise)

1. ~~Recording fidelity~~ **Decided (owner, 2026-10-16):** coarse everywhere, meaning the offscreen correction tier for every unit (checked every 1 s, corrected past 2 tiles). The fine tier, a config knob and adaptive quality were not chosen for now; Task 18 still reports the recorder's real file rate, so this can be revisited with numbers.
2. **Seek keyframes:** not in v0.10 unless decode-from-start seeking takes over ~5 s on a 30-minute 8-player recording.
3. **Overlay hotkeys:** F1–F9 in development builds.
4. **Dev and test matches:** recorded only when `Replays/Enabled` is on and the match isn't a perf run (`-perf`) or the menu battle.
5. **Replay ownership:** players may share the file freely; there is no signature or anti-tamper (a tampered replay only fools its own viewer).

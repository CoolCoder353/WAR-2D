# v0.6 Command — Design

**Status:** approved in brainstorming with the owner on 2026-10-09; awaiting written-spec review.
**Parent:** [roadmap design spec](2026-10-05-war2d-roadmap-design.md) §3 (v0.6) and §6 (UI/UX). Where this document differs from the parent, this document wins for v0.6 and the parent's decisions log is updated when v0.6 lands (see §9).

## 1. Goal

Make the game commandable at 10,000 units per player: a HUD, menus, lobby and settings built in UI Toolkit to an owner-approved Figma design, the missing orders (Attack-move, Stop, Hold, Shift-queue), and player-controlled diplomacy. First, close the debt v0.5 handed over (gate, KCP tuning, play-test).

## 2. Decisions (from brainstorming)

| Topic | Decision |
|---|---|
| v0.5 debt | Cleared **first**, before UI work (phases 0–1). |
| Orders | Move, Attack-move, Hold, Stop and Shift-queue end to end. Dig and Repair wait for v0.7 and are not on the command card. |
| Move semantics | Today's Move (units stop for enemies in range) becomes **Attack-move**. The new **Move** ignores enemies until it arrives. |
| Map choice | Generator presets: 256² / 512² / 1024² plus a seed (random or typed). Lobby shows a **preview** to every player; the server owner has a **Reroll** button. |
| UI technology | **Staged full migration to UI Toolkit.** uGUI is removed from the shipped scenes by the end of v0.6. |
| UX approval | **Every v0.6 screen is designed in Figma and approved by the owner before any UI production code is written.** Claude drafts the Figma file; the owner reviews and approves. |
| Visual style | Functional placeholder, entirely driven by design tokens, so v0.8 restyles tokens rather than screens. |
| Gifting | To **any** player, ally or not. |
| Diplomacy | A lobby toggle on top of FFA or Teams. Per player, a private **attack list** and a separate **share-vision list**, editable mid-match. |
| Diplomacy win | The match ends when no two remaining HQ holders attack each other in either direction; they all win. |
| Diplomacy privacy | Attack lists are **fully private**: never sent to any other client. |

### Phase 2: Orders

**Data:** a `Stance` byte on the `Unit` component (`Idle`, `Move`, `AttackMove`, `Hold`), gathered into a `SimData.Stance` SoA array like every other unit field. Queued waypoints live in a server-side `WaypointBook` (unit id → up to `Orders/MaxQueued` (goal, stance) pairs, `GameConfig.xml`, default 4), so only units that have a queue cost memory.

**Behaviour** (inside existing Burst stages):

| Stance | Behaviour |
|---|---|
| Move | Follows its flow field and does **not** acquire targets until it arrives; then `Idle`. |
| AttackMove | Current behaviour: stops to fight a target in range, resumes when it is gone. |
| Hold | Drops its order, never moves on its own, and is not pushed by separation. Fires at targets in range. |
| Idle | Fires at targets in range; does not chase. |
| Stop (command) | Clears order and queue; unit becomes `Idle`. |

**Shift-queue:** appends one waypoint per ordered unit in the `WaypointBook`; a full queue drops the new waypoint. When a unit arrives, the movement write-back reports its id on a `SimData.Arrivals` queue; at the tick boundary `SimCommandSystem` groups advancing units by (goal, stance) and issues one `OrderBook.Issue` per group, so shared routes still share flow fields.

**Network:** `OrderCommands` gains `OrderKind` (Move / AttackMove / Hold / Stop) and a `Queue` flag, keeping the chunked id accumulation and the squad path. Gate + validator: kind in range, ownership, goal inside the map. No new client-bound unit data; each new leg replicates as a new route.

**Input:** A + click attack-move, S stop, H hold, Shift queues. Rebindable in phase 5.

### Phase 2b: Diplomacy

**Model.** Per player slot, two server-only 16-bit masks (one bit per owner slot, `SimData.MaxOwners` = 16), held authoritatively by a main-thread `Diplomacy` object and copied into `SimData` at the tick boundary so Burst can read them:
- `AttackMask[slot]`: players whose units and buildings this player's units target.
- `ShareVisionMask[slot]`: players who receive this player's vision.

Teams (`GameCore.Teams`, lobby) are only the **starting state**: teammates are off each other's `AttackMask` and on each other's `ShareVisionMask`; everyone else is on `AttackMask` and off `ShareVisionMask`.

**Lobby toggle `Diplomacy`.** Off: the masks never change (plays exactly like v0.5). On: `Cmd_SetAttack(targetOwner, bool)` and `Cmd_SetShareVision(targetOwner, bool)` during *Playing*, gated, validated (target is another live player), with a per-player cooldown `Diplomacy/ChangeCooldownSeconds` in `GameConfig.xml`. Applied at the tick boundary as `SimCommand`s.

**Combat.** A unit of slot `a` may target an entity of slot `b` only if bit `b` of `AttackMask[a]` is set. Relations are asymmetric: P1 can attack only P3 while P2 still attacks P1. Damage only comes from targeting, so a player not on your attack list never takes damage from you (v0.7 bomb blasts remain the stated exception).

**Fog.** Fog grids become **per receiving player** (one per owner slot). Each sight source is stamped into its owner's grid and into the grid of every player in its owner's `ShareVisionMask`, so a player's grid is the union of their own sight and everything shared with them. With no sharing, the cost equals v0.5's FFA case. A receiver's explored memory only grows from the moment sharing starts. Explored memory, `FogBatch`, unit interest and `BuildingInterest` are computed per **receiver** from that union.

**Win/loss.** During *Playing* the match ends when no two remaining HQ holders have each other on their attack masks in either direction; all of them win. With Diplomacy off this reduces to v0.5's "one team left" rule, so `WinLossRules` has one rule. A single remaining HQ holder still wins; none remaining is still a draw.

**Privacy.** Attack masks are never serialised to any client other than their owner (the owner's own masks reach them for the HUD). A receiver necessarily learns that someone shares vision with them (they start receiving that fog); it is shown to them explicitly. `LeakTests` covers: no client ever receives another player's `AttackMask`; fog and interest never exceed the receiver's union.

**Vocabulary.** "Enemy" (CLAUDE.md, code comments) changes from "a different team" to "a player on my attack mask". `TeamRules` becomes the place this is decided.

### Phase D: UX design in Figma

Claude creates one Figma file via the Figma connector and the owner reviews it there.

- **Tokens** as Figma variables: colours (with the standard, colour-blind-safe and high-contrast palette sets), spacing, type scale, radii. These export one-for-one to `Assets/UI/Theme.uss`.
- **Frames** for every screen and state:
  - HUD: top bar, minimap, selection panel, command card, squad bar, alert feed, diplomacy panel, gift dialog
  - main menu, host and join
  - lobby, including the map preview, Reroll, the Diplomacy toggle and ready states
  - in-match menu, surrender confirmation
  - end screen with stats
  - settings, including the rebinding flow
- **Approval gate:** the owner approves the file. The plan records the Figma link, the approved version and the date. **No UI production code (phases 3–5) starts before approval.** Any later change to an approved screen is made in Figma and re-approved before code.

### Phase 3: UI foundation + HUD

- `Theme.uss` from the Figma tokens; one `UIDocument` per scene (`Main_Menu`, `Map_2`) sharing a `PanelSettings` that scales with screen size from a 1920×1080 reference.
- Each screen = UXML + a thin controller bound to a **plain C# model** (`HudModel`, `LobbyModel`, `SettingsModel`) with change events. Models are filled only from data the client already legitimately receives, and are EditMode-testable without a scene.

| HUD piece | Data source | New server work |
|---|---|---|
| Top bar: resources, income/s, upkeep/s, player list, gift button | Owner-only resource TargetRpc; `GameCore` player list | `ServerPlayer` adds last-second income and upkeep to the TargetRpc |
| Diplomacy panel (when enabled): per-player attack and share-vision toggles; "sharing vision with you" markers | Owner's own masks (TargetRpc) | Owner-only mask echo; share-received notice to the receiver |
| Selection panel: counts per type, click to filter, combined health | `ClientWorld` | — |
| Command card: Move, Attack-move, Stop, Hold, build menu, spawner production queue (+ / − / count) | Phase 2 commands, existing placement flow | Gated **dequeue** command (unit cost is charged at spawn, so nothing to refund) |
| Squad bar 1–0 with counts | Server squads | Owner-only squad-count update |
| Minimap: fog, own and visible units, buildings and ghosts; click moves camera, right-click orders, alert pings | `FogView` grid, `ClientWorld`, building records; texture redrawn at 5 Hz | — |
| Alert feed + pings: under attack, upkeep unpaid, gift received, vision shared with you; hooks for construction finished and bomb triggered (v0.7) | — | Owner-only `AlertBatch` TargetRpc, throttled per area; positions are always the receiver's own entities |

Replaces uGUI `ResourceUI` and `HQPlacementUI`. Health bars stay instanced.

### Phase 4: Menus, lobby, match setup

- **Main menu:** Play (host / join by IP), Settings, Quit.
- **Match settings:** host-only `Cmd_SetMatchSettings(mode, diplomacy, mapPreset, seed, startingResources)`, validated against a new `<Lobby>` section in `GameConfig.xml` (allowed map sizes, allowed starting resources). Held in one public SyncVar on `GameCore`; overrides `Match/Map` at match start. Any change clears every player's ready flag.
- **Map preview:** every client regenerates the map from (size, seed) off the main thread when the settings change and shows a downscaled thumbnail with the HQ clearings marked. Clients already regenerate the full map at match start, so the preview reveals nothing new. **Reroll** (server owner only) picks a new random seed.
- **Per player:** `Cmd_SetColour` (unique within the active palette), `Cmd_SetReady`, and in Teams mode `Cmd_SetTeam` for oneself (the server owner can still move anyone). FFA forces solo teams.
- **Start:** server owner only, when every player is ready and the starting masks contain at least one attacking pair (otherwise the match would end at once).
- **Gifting:** `Cmd_GiftResources(targetOwner, amount)` to any other live player, during *Playing*, `1 ≤ amount ≤ balance`, cooldown `Gifting/CooldownSeconds`. Sender and recipient are told via TargetRpc (recipient learns sender and amount only).
- **In-match menu:** settings, leave, surrender (`Cmd_Surrender` eliminates the player exactly like losing their HQ). Nothing pauses.
- **End screen stats:** per player: units built / lost / killed, buildings built / lost, resources mined / spent / gifted, peak army. Tracked on the server, sent to everyone at *GameOver* only.
- Old uGUI lobby, menu and HQ-placement UI deleted.

### Phase 5: Settings + controls

- Settings JSON in `Application.persistentDataPath`; key overrides via the Input System's override JSON.
- **Graphics:** resolution, fullscreen, vsync, FPS cap. **Audio:** an `AudioMixer` with master / music / SFX groups (nothing plays until v0.8). (UI scale was dropped at the Figma gate, 2026-10-09.)
- **Palettes:** standard, colour-blind-safe (Okabe–Ito based), high-contrast. One palette source feeds unit tints (`InstancedUnitRenderer.TeamColors` today), buildings, the minimap and the UI tokens.
- **Camera and selection:** edge scroll (toggle), middle-drag pan, zoom towards the cursor, double-tap a squad key to centre on it, double-click to select that unit type on screen.
- **Full rebinding** of every action.

### Phase 6: Close-out

- PlayMode coverage of every UI flow: menu → host → lobby (settings, preview, reroll, ready) → start; HUD orders and command card; production dequeue; diplomacy toggles; gifting; surrender → end screen; settings and rebinds persist across restarts.
- Dev console and perf overlays compiled out of non-development builds; a test asserts it.
- Gate re-run within roadmap §4, results in `docs/perf/v0.6/`.
- A full manual Linux match played only through the new UI, including a Diplomacy match with at least 3 players.
- Docs: `gameplay.md`, `architecture.md`, `known-issues.md`, `roadmap.md`, `CLAUDE.md` (enemy definition, UI conventions, Figma gate).

## 4. Security and leaks

Every new command calls `CommandGate.Allow(sender, nameof(...))` first and validates server-side: `Cmd_SetMatchSettings`, `Cmd_SetColour`, `Cmd_SetReady`, `Cmd_SetTeam`, `Cmd_SetAttack`, `Cmd_SetShareVision`, `Cmd_GiftResources`, `Cmd_Surrender`, the dequeue command and the extended order commands. Each gets fuzz cases in `FuzzTests`.

New `LeakTests` cases:
- no client receives another player's `AttackMask`
- fog, unit interest and building interest never exceed the receiver's vision union
- alerts only carry the receiver's own entities
- match stats are never sent before *GameOver*
- gift notices go only to the sender and recipient

## 5. Testing

- **EditMode:**
  - stances: Move passes enemies, Attack-move stops, Hold is never pushed, Stop clears
  - Shift-queue order and cap
  - asymmetric targeting
  - vision union and explored memory per receiver
  - the generalised win rule, including the v0.5 team cases
  - validators for every new command
  - model classes (`HudModel`, `LobbyModel`, `SettingsModel`)
  - a check that every map preset fits 8 HQ clearings
- **PlayMode:** the flows listed in phase 6.
- **Performance:** gates in phases 0, 1 and 6. Per-player fog and the vision union must keep the tick within budget.

## 6. Exit criteria

- All EditMode and PlayMode tests pass.
- Gate within roadmap §4 (`docs/perf/v0.6/`).
- Every UI flow has PlayMode coverage; no debug UI in non-development builds.
- All shipped UI matches the owner-approved Figma version.
- A full manual Linux match through the new UI, including a 3+ player Diplomacy match.
- No open `known-issues.md` item targeted at v0.6.

## 7. Out of scope

Dig and Repair orders, the tutorial, the Steam server browser (v0.9), final art and audio (v0.8), instanced buildings and walls (v0.7), the Windows build profile (v0.9 unless the owner pulls it in).

## 8. Effects on later versions

- **v0.7 hidden bombs** are hidden from every client that does not receive the owner's vision (replaces "enemy clients"). Bomb blasts still damage everything in radius.
- **v0.8** restyles the Figma tokens and `Theme.uss`; screen structure stays.

## 9. Parent-spec decisions superseded on landing

| Parent decision | Becomes |
|---|---|
| Teams fixed at match start; allies share vision and never fight | Teams are the starting state; with Diplomacy on, attack and vision-share lists change mid-match |
| Win = last team with an HQ | Win = remaining HQ holders are mutually non-attacking |
| Fog per team | Fog per player; vision = own ∪ shared-to-me |
| Resource gifting to allies | Gifting to any player |
| Lobby: host picks map | Host picks size preset and seed, with preview and reroll |

# WAR-2D Roadmap Design (v0.2 – v0.9)

- **Date:** 2026-10-05
- **Status:** Approved in brainstorming. Waiting for written-spec review.
- **Authors:** project owner + Claude
- **Related:** [architecture.md](../../architecture.md), [gameplay.md](../../gameplay.md), [known-issues.md](../../known-issues.md)

## 1. Vision

WAR-2D is a pixel-art 2D RTS for Steam (Linux and Windows) whose distinguishing feature is **army scale**: each player can run **10,000 active units**. Matches have up to **8 players** (so up to **80,000 units**), in **free-for-all or team** modes. The game must be **secure**: no client ever receives information its team isn't allowed to know. Every update should leave the game as bug-free as possible.

New gameplay on the roadmap:
- **Builder units** construct everything except the HQ.
- **Buildable walls.**
- **Digger** siege units that tunnel through terrain and walls.
- **Hidden bombs** that only the owning team can see.

Also planned: a full UI/UX overhaul, upgraded pixel art and audio, and Steam integration.

## 2. Decisions log

| Topic | Decision |
|---|---|
| Unit target | 10,000 units **per player**. Up to 8 players means 80,000 units per match. |
| Players / modes | Up to 8 players. FFA **and** team modes (2–4 teams). |
| Network model | **Server-authoritative hybrid**: the server sends paths plus corrections, not per-tick state. Lockstep was rejected because it leaks hidden information and requires fixed-point determinism. |
| Fog of war | Real fog of war, **line of sight** (walls block vision), explored terrain remembered, per team. |
| Hosting | Player-hosted **and** dedicated servers. |
| Online services | **Steam** (Steamworks lobbies, relay, auth). Transport: FizzySteamworks for Mirror. |
| Control | Unlimited box select plus **squads** (server-side, hotkeyed). |
| Sequencing | Foundation first → scale spike → core rebuild → features. |
| Render pipeline | Move from HDRP to **URP 2D** with Pixel Perfect Camera. |
| UI framework | **UI Toolkit** for menus and HUD. Instanced world-space health bars. |
| Art | Consistent **pixel-art** set. Method (code-generated by Claude, or AI image tool + Claude pipeline) chosen by prototype at the start of v0.8. |
| Audio | In v0.8. SFX from an sfxr-style generator script. Music from a **code-generated chiptune** generator. |
| Tutorial | Out of scope. Will be added later, once the game is more complete. |
| CI | None. Tests are run **locally** with a batch-mode script. |
| Team | Project owner + Claude. Small, shippable updates. |
| Commits | **No co-author attribution**, ever (see `CLAUDE.md`). |
| Perf reference machine | Ryzen 5 5600GT (6C/12T), 32 GB RAM, Radeon RX 6600, Linux. |
| Unpaid upkeep | Entities whose upkeep can't be paid **decay**: they lose `DecayPercentPerSecond` of max health per second until paid. Resources never go negative. |
| Spawn rate | `SpawnRate` is used: a spawner produces at most `SpawnRate` units per second from its queue. |
| Elimination / leaving | When a player is eliminated or disconnects, **all their units and buildings are destroyed, each with an explosion**. |
| Death explosions | Every entity death (combat, decay, elimination) plays an explosion. The server sends each client only the explosions inside that client's view. |
| Legacy code | Deleted in v0.2 (git history keeps it). The lobby row prefab is in use, so it is renamed, not deleted. |
| Windows verification | Deferred out of v0.2. The Windows build profile is still added. |
| Editor automation | The Unity Pipeline package (`com.unity.pipeline`) is installed. Scene and asset edits and test runs go through the live editor (`unity command ...`). |

### 3.1 v0.2 scope detail (from `known-issues.md`)

- **Config:** delete `ResourceConfigLoader`. All costs come from `GameConfig.xml` through `ConfigLoader`. Remove or wire up `GameManagerSettings`. Use `SpawnRate` (or remove it). Move unit range, attack interval and acceleration into config. Validate the schema at load and fail loudly on bad values.
- **Logic:**
  - Fix `MovementSystem.IsAvaliable`.
  - Fix `targetId` to use unit ids.
  - Clean up the registry and release tiles when an entity is destroyed.
  - Remove disconnected players from `ServerPlayers`.
  - Fix Shift so it works while held.
  - Use a single countdown, owned by the server.
  - Reset per-match state.
  - Real draw handling.
  - No passive income for eliminated players.
  - `TryAddBuilding` checks the game state.
  - Decide what happens when upkeep can't be paid.
- **Networking:** a dedicated server can start a match (the server owner is the first client). Send camera view updates only when they change and at a capped rate. Remove the per-frame `SetServerPlayer` JSON (resources are sent once, on change). Replace random IDs with an allocator. Make the match scene configurable.
- **Security:** a central command validator (ownership, `GameState`, value ranges, NaN/out-of-map), per-connection token-bucket rate limits, and a maximum message size.
- **Economy:** passive income only for players still in the game. Unpaid upkeep causes decay (see the decisions log). Spawners honour `SpawnRate`.
- **Elimination:** eliminated or disconnected players lose all their entities, with death explosions sent per client view.
- **Pathfinding and spawning:** dispose path buffers (memory leak), spawn units on the nearest free tile outside the spawner footprint, keep only the Octile heuristic and remove the broken alternatives.
- **Building footprints:** move them into `GameConfig.xml` (`Width`/`Height`) instead of deriving them from sprite size. This removes the client round-trip `GetTilesBuildingWillCoverCommand`.
- **Camera:** switch to an orthographic camera (zoom via `orthographicSize`). The Pixel Perfect Camera waits until v0.8, when all art shares one pixels-per-unit.
- **Hygiene:** URP 2D, new Input System only, remove unused packages (`ai.navigation`, `cinemachine`, `timeline`, `visualscripting`), Windows build profile, remove legacy/WIP code (or mark it clearly as kept), replace tag-based menu wiring with serialized references.

## 4. Target architecture

### 4.1 Performance budgets (reference machine, player host = server + client)

| Metric | Target |
|---|---|
| Server simulation | 20 ticks/s, **≤ 25 ms per tick** at 80,000 units |
| Client frame rate | **≥ 60 fps** with 10,000 own units on screen |
| Bandwidth per client | **≤ 128 KB/s average**, ≤ 256 KB/s peak |
| Host upload (7 remote clients) | about 7 Mbps average |

### 4.2 Simulation (server, ECS only)

- **Tile map:** an ECS singleton holding a flat `NativeArray` grid, plus a sector index (32×32 sectors). `WorldStateManager` becomes a thin Mirror bridge: it validates commands, puts them in a queue, and an ECS system applies them at the start of the next tick.
- **Fixed tick:** gameplay systems run at 20 Hz in a fixed-step group. Clients interpolate between ticks.
- **Pathfinding:** a **flow field** per move order (goal), shared by every unit in that order and cached by goal. Terrain changes (dig, walls) invalidate only the affected sectors. Steering adds separation so units don't stack. Group goals are spread over free cells near the target.
- **Spatial hash:** a uniform bucket grid rebuilt every tick with parallel jobs. Used for target finding, separation, bomb triggers and blast queries.
- **Combat:** target search is time-sliced (each unit re-searches every N ticks). Damage = base damage × `DamageTable[attackerType][targetClass]`, where target class is Unit, Building or Wall.
- **IDs:** a server-side allocator gives each object a 32-bit network ID made of an index plus a reuse counter. It's independent of `Entity`, and objects are always referred to by network ID.

### 4.3 Replication

- Custom bit-packed `NetworkMessage`s replace the SyncLists.
- **Movement:** when a unit receives an order, the server sends its waypoints (taken from the flow field), start tick and speed **once**. Clients move the unit along that route themselves. Corrections are sent when a unit is pushed, blocked or fighting, on the unreliable channel.
- **Health:** 1 byte, sent only when it changes.
- **Reliable events:** spawn, despawn, death, explosion, construction progress milestones.
- **What each client receives:**
  - all of its own team's units and structures
  - enemy entities on tiles its team can currently see
  - **never** enemy bombs (or any object with a stealth flag), enemy resources, or enemy fog grids
- **Orders:** a list of selected unit network IDs (delta and varint encoded, sent in chunks), **or** a squad ID. The server checks every ID belongs to the sender.

### 4.4 Fog of war

- Each team has a visibility grid (1 byte per tile) and an explored grid. They're recomputed at 5 Hz with **symmetric shadowcasting** in parallel Burst jobs. Walls and rock block sight.
- Vision sources are deduplicated by (tile, radius) before casting.
- Clients receive changes to their own team's grids only. Explored terrain is remembered on the client: terrain as it was when last seen, with enemy-built walls shown only once seen.

### 4.5 Rendering (client)

- Units are drawn with GPU instancing (BatchRendererGroup or `RenderMeshInstanced`) from a sprite atlas, with per-instance position, rotation, frame and team colour. One draw call per atlas.
- Health bars are instanced, shown only for damaged or selected units.
- Buildings and walls use pooled GameObjects or instancing, whichever the spike shows is better.

## 5. Gameplay rules (all values configurable in `GameConfig.xml`)

### 5.1 Teams and modes

- The lobby offers FFA or Teams (2–4 teams, up to 8 players).
- Allies share vision and can't damage each other. The one exception is bomb blasts, which hit friendly units too.
- Each player keeps **separate resources** and can **gift** resources to an ally.
- A player is eliminated when they lose their HQ. A team is out when all its HQs are gone. The last team with an HQ wins. If everyone is out in the same check, it's a draw.

### 5.2 Builder and construction

- The HQ has a production queue for Builders. This may change later.
- Placing a building creates a **blueprint**. The full cost is taken at placement and refunded in full if the blueprint is cancelled before construction starts.
- Each Builder adds `BuildPower` per second. More Builders build faster.
- A building under construction has health in proportion to its progress and can be attacked.
- Builders build every type except the HQ. They don't attack.
- **Repair:** Builders repair damaged own or allied buildings and walls over time. Repair costs resources (`RepairCostPerHp`) and runs at `RepairRate`.

### 5.3 Walls

- Drag to place a straight line (horizontal, vertical or diagonal) of 1×1 wall segments. Each segment is its own blueprint.
- Walls block movement and line of sight, have health and can be destroyed. A destroyed wall becomes floor.

### 5.4 Digger (siege unit)

- Right-click a rock or wall tile to dig toward the clicked point, tile by tile, `DigTime` seconds per tile.
- Rock becomes floor. **Gem tiles pay out `GemDigPayout`** and then become floor, so any Miner facing that tile stops producing.
- **Map border tiles can't be dug.**
- It can fight, but the damage table makes it weak against units and strong against buildings and walls.

### 5.5 Hidden bombs

- A 1×1 trap built by Builders from the build menu.
- **Limited only by cost and upkeep** (no count cap). Bombs have an upfront cost and a running cost like other buildings.
- From blueprint placement onward, the bomb is never sent to enemy clients. Enemies can see the Builder working at that spot.
- It explodes when **any enemy unit** enters its tile. It deals `BlastDamage` to **everything** within `BlastRadius`, including friendly units, buildings and walls.
- Everyone with vision of the tile sees the explosion. No detection counter in this roadmap.

### 5.6 Unchanged

Miner (must face a gem), Small Unit Spawner + Tank, passive income, upkeep. The rule for unaffordable upkeep is decided in v0.2.

## 6. UI/UX (v0.6)

- **HUD:**
  - Top bar: resources with live income and upkeep, player and team list, gift button.
  - Minimap: respects fog, click to move the camera, right-click to order, alert pings.
  - Selection panel: counts per type, click a type to filter, combined health.
  - Command card: contextual build menu, production queues, Move, Attack-move, Stop, Hold, Dig, Repair.
  - Squad bar: keys 1–0.
  - Alert feed.
- **Controls** (all rebindable):
  - Camera: WASD, edge scroll (can be turned off), middle-drag pan, zoom towards the cursor.
  - Selection: unlimited box select, Shift to add, double-click to select that type on screen.
  - Squads: Ctrl+N creates, N selects, double-tap centres.
  - Orders: right-click, A attack-move, S stop, H hold, Shift queues.
  - Building: R rotates, drag places walls, Esc cancels.
- **Menus:**
  - Main menu: Play, Settings, Quit.
  - Host or join by IP (the Steam browser replaces this in v0.9).
  - Lobby: nickname, team, colour, ready. The host sets mode, map and starting resources.
  - In-match menu: settings, leave, surrender. Nothing pauses.
  - End screen with match stats.
- **Settings:**
  - Graphics: resolution, fullscreen, vsync, FPS cap.
  - Audio: master, music and SFX volume.
  - Controls: full rebinding.
  - UI scale.
  - Colour-blind-safe and high-contrast team palettes.

## 7. Art and audio (v0.8)

1. **Method prototype:** make the same few sprites (one unit, one building, one tile set) with (a) Claude code generation and (b) an AI image tool plus Claude clean-up. The owner picks one.
2. **Style guide:** palette, tile size, pixels-per-unit, how team colours are applied, frame counts for each animation, UI style.
3. **Pipeline:** generator scripts or source exports → an import script (palette mapping, team-colour masks, atlas packing, Unity import settings: point filter, no compression) → owner review before merge.
4. **Audio:** an sfxr-style SFX generator script and a procedural chiptune music generator, both checked into the repo. Their outputs are committed as assets.
5. **Steam:** declare AI-generated content in the Steam content survey.

## 8. Quality and security process

- **Branching:** one branch per update, a PR for each feature into it. No co-author lines in commits or PRs.
- **Tests (local, batch mode):** a script runs Unity edit-mode and play-mode tests from the command line.
  - Edit-mode tests: placement, damage table, config parsing and validation, flow fields, line of sight, ID allocator, command validators, economy.
  - Play-mode tests: host + client match flow; **leak tests** asserting that no hidden data (enemy fog, stealth objects, enemy resources) is serialised to a client.
  - Fuzz tests: random and malformed input to every command validator.
  - Performance tests: Unity Performance Testing package, gated on §4.1.
- **Review gate:** a security review and a code review before every merge. `known-issues.md`, the docs and `CLAUDE.md` are updated in the same PR.
- **Definition of done (per update):**
  - all tests pass
  - §4.1 targets met (from v0.4 on)
  - no open known issue targeted at that version
  - a full match played on Linux and Windows

## 9. Risks

| Risk | Mitigation |
|---|---|
| Line-of-sight fog too slow at 80k units | Measured in v0.3. Fallbacks: lower update rate, coarser vision grid, or radius-only vision for units with LOS only for structures. |
| Host upload too high for home connections with 8 players | Measured in v0.3. Fallbacks: lower correction rate, coarser quantisation, recommend dedicated servers for 8-player matches. |
| Instanced sprite rendering complexity in URP 2D | Prototyped in v0.3 before committing. |
| Mirror message size and throughput limits at this scale | Spike measures it. Chunk large messages. KCP and Steam transport settings tuned in v0.5 and v0.9. |
| Code-generated art quality ceiling | v0.8 method prototype before committing. |
| Scope creep in a two-person team | Each update has fixed scope and exit criteria. New ideas go to a backlog, not into the current update. |

## 10. Out of scope (this roadmap)

Tutorial and onboarding, ranked matchmaking, player accounts beyond Steam identity, replays, bomb detection units, AI opponents, mobile or console platforms.

# v0.12 Arsenal Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. This plan lists each task's files, steps and tests; write the code against the files as they are when you start (read them first).
> Project rules that apply to every task: compile with `tools/unity-compile.sh` while working; run **both** suites (`tools/unity-test.sh EditMode`, `tools/unity-test.sh PlayMode`) **once at the end of the whole plan** (the owner's preference, 2026-10-16), not after every edit. Commit only when the owner has asked for it, on `release/v0.12`, never from `main`, and **never add a co-author or AI attribution line** (`CLAUDE.md`). ## Global constraints

- Server-authoritative as always: units are created only by `SimCommandSystem`; main-thread code never touches `Unit` entities or `SimData` arrays between ticks; new tick stages declare write access to `Unit` and schedule Burst jobs on `state.Dependency`. `ApplyDamageJob` stays the single writer of unit health.
- Every new or changed `[Command]`: `requiresAuthority = false`, `NetworkConnectionToClient sender = null`, `CommandGate.Allow` first (with a budget entry), ownership and value checks (`CommandValidator`), *Playing* only, at most `MaxSpawnersPerCommand` buildings; fuzz tests for each.
- Every balance number in `GameConfig.xml`, parsed strictly. No new hard-coded numbers.
- "Enemy" means an owner on the attacker's attack mask (`SimData.AttackMask`), never just a different owner.
- No new replication message kinds (spec §5): clients draw splash and blasts from the attack events and the unit type. `LeakTests` must keep passing.
- Any HUD change beyond the approved frames goes back through Figma first.
- Perf budget: ≤ 25 ms main-thread tick p95 at 80,000 units with the mixed roster (`tools/perf-run.sh`); results in `docs/perf/v0.12/`.

### Task 4: Armour classes

### Task 5: Fire only at what your side sees

**Files:** `Sim/SimCombatSystem.cs` (target search), `Sim/SimVisionSystem.cs` (read `SimData.Visible`), tests.

- [ ] Target search requires the target's fog cell visible on the attacker owner's grid (spec §4.1); shared vision counts.
- [ ] Tests: an enemy in range but in the fog is not targeted; a Scout or Radar lighting it makes Artillery fire.

### Task 6: Splash and minimum range

**Files:** `Sim/SimCombatSystem.cs` (a splash job between the attack job and `ApplyDamageJob`), the wall-damage queue, `UI/Controllers/HudController.cs` (role line), tests.

- [ ] Units with `Splash` > 0 queue a splash hit at the target's position; the splash job walks the spatial hash and queues damage for every **enemy** unit and building in the radius, 100 % at the centre to 50 % at the edge, times the target's class multiplier; walls in the radius through the wall-damage queue. Allies are not hit.
- [ ] `MinRange`: targets closer than it are ignored and the search goes on.
- [ ] Role line in the hover card: "Range 14, splash 2, can't fire closer than 4" (Figma).
- [ ] Tests: falloff, enemies only, walls, single writer, min range.

### Task 7: The large pathing class

**Files:** `Sim/SimCommandSystem.cs` (spawn), `Sim/SimCommandSystem.Move.cs` (`moversByClass`), `Pathing/*`, spawner free-tile search, footprint push-outs, `docs/bug-review.md`.

- [ ] Heavy and Artillery use `FlowSizeClass.Large`. Fix the `bug-review.md` items: assert `SizeClass < FlowSizeClass.Count` at spawn, `moversByClass` buckets per class (no `& 1`), spawners search for a free tile with large clearance, push-outs respect clearance.
- [ ] Tests: a large unit paths through a 3-wide choke and is refused at a 1-wide gap.

### Task 8: Client drawing and sound for the new weapons

- [ ] Per attacker type: Sniper → `SniperTracer`; Artillery → `ArtilleryShell` in flight, then `ShellImpact` at the target; Flamethrower → `FlameStream` stretched from the nozzle to the target; Heavy and Scout → the existing tracer and muzzle flash. Splash radius from config (no new messages).
- [ ] Sounds through `AudioService` from the same events: `shot_<type>`, `shell_impact`, `bomber_blast`.
- [ ] `LeakTests`: splash and blasts never produce messages about units outside a client's interest.

### Task 9: The Suicide bomber

**Files:** `Sim/Stances.cs` (`OrderKind.Detonate`), the bomber logic (a tick stage or the combat stage), `Sim/SimBombSystem.cs` (shared blast), `Client/GameInput.cs` (a rebindable `Detonate` action on **B**), `UnitCommander` (`Order(Detonate)`), `UI/Controllers/CommandCardController.cs`, tests.

- [ ] Attack-move (or idle with an enemy in range): target the nearest enemy unit or building, run at it, detonate on contact (target within 0.8 tiles of its body edge). Detonate order: every selected bomber at once.
- [ ] The blast reuses the bomb's path: every unit, building and wall tile in `BlastRadius`, **friends included**, with the bomber's damage-table multipliers. A bomber killed before contact does not explode (owner).
- [ ] Input: `Detonate` action on B (the Controls row and `cmd-detonate` appear by themselves once it exists); replace the `Enum.TryParse` lookups for `OrderKind.Detonate` and `UnitType.SuicideBomber` in the command card with direct references.
- [ ] Tests: contact, Detonate order, friends in the blast, no blast when killed; a PlayMode bomber run on an enemy building.

# v0.6 "Command" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make WAR-2D commandable at 10,000 units per player. That means four things:
- a UI Toolkit HUD, menus, lobby and settings, built to an owner-approved Figma design
- the missing orders: Attack-move, Stop, Hold and Shift-queue
- player-controlled diplomacy
- closing the debt v0.5 left behind first

**Architecture:**
- **Debt first:** the first tasks measure and tune the v0.5 networking.
- **Sim work:** orders and diplomacy extend the async tick. Per-unit state goes on `Unit` and is gathered into `SimData`. Main-thread state (`WaypointBook`, `Diplomacy`) is applied only at the tick boundary.
- **UI:** built to the approved Figma file. Every screen is UXML plus a thin controller over a plain C# model that only holds data the client already receives. uGUI is removed by the end.

**Tech Stack:** Unity 6000.4.1f1, Entities 6.4, Burst 1.8, Collections 2.x, Mirror 96 + kcp2k, URP 17.4 (2D), UI Toolkit (`com.unity.modules.uielements`), Input System 1.19, Unity Test Framework 1.6, Performance Testing 3.0. Design: Figma, via the Figma connector.

## Global Constraints

- Unity editor **6000.4.1f1**, open on the project. Compile with `tools/unity-compile.sh`, test with `tools/unity-test.sh EditMode` and `tools/unity-test.sh PlayMode`. **Both suites must pass at the end of every task.**
- **Performance budget (roadmap §4):**
  - host main-thread tick **≤ 25 ms p95** at 80,000 units
  - client **≥ 60 fps** with 10,000 own units on screen
  - **≤ 256 KB/s average and ≤ 768 KB/s peak (1 s)** per client
- **Every gameplay and tuning number lives in `Assets/Resources/GameConfig.xml`**, parsed strictly by `Config.ConfigParser`, with a `ConfigParserTests` case for each new field (valid, missing, out of range).
- **The server owns the world.** Main-thread code never touches `Unit` entities or `SimData` arrays between ticks. It queues a `SimCommand`, or reads at `SimContext.Settled`.
- **Every `[Command]`:**
  - `requiresAuthority = false`, with a `NetworkConnectionToClient sender = null` parameter
  - calls `CommandGate.Allow(sender, nameof(...))` first, and has a rate budget in `CommandGate`
  - validates every argument server-side (ownership via `BuildingData.UIntToInt(sender.identity.netId)`, game state, ranges in `CommandValidator`)
  - has a `FuzzTests` case
- **Clients only see what they are allowed to see.** Anything new sent to clients gets a `LeakTests` case. Private per-player data goes through TargetRpc, never a SyncVar.
- **⛔ Figma gate:** **no UI production code (Tasks 8–14) is written until Task 7's Figma design is approved by the owner.** Shipped UI matches the approved version. A change to an approved screen goes back through Figma first.
- **UI:** UI Toolkit only for new UI. Colours, spacing and type come from `Theme.uss` variables, never literals in UXML or C#.
- **Never hand-edit `.unity`, `.prefab` or `.asset` YAML.** Use the live editor (`unity command ...`). New assets get their `.meta` from the editor.
- **Don't edit vendored code** (`Assets/Mirror/`, `Assets/Plugins/Demigiant/`, `Assets/3rd Party/`).
- **Branch:** `release/v0.6`, one PR per phase into it. **Never** a `Co-Authored-By:` line or any AI attribution in commits or PRs (`CLAUDE.md`).
- **Docs:** update `gameplay.md`, `architecture.md`, `known-issues.md` and `CLAUDE.md` in the task that changes the behaviour they describe.

**Interfaces (produces):**
```csharp
namespace WAR2D.Sim
{
    /// <summary>Server-side queued waypoints per unit id. Main thread only, touched at the tick boundary.</summary>
    public sealed class WaypointBook
    {
        public WaypointBook(int maxQueued);
        public void Append(int unitId, int2 goal, byte stance);       // drops when full
        public bool TryPop(int unitId, out int2 goal, out byte stance);
        public void Clear(int unitId);                                // a non-queued order or Stop
        public void Forget(int unitId);                               // death
        public int CountOf(int unitId);
    }
}
// SimData gains: public NativeQueue<int> Arrivals;  // ids of units that arrived this tick
// SimContext gains: public WaypointBook Waypoints { get; }
// OrdersConfig { int MaxQueued }  in GameConfigData.Orders
```

**Rules:**
- A **non-queued** order clears each unit's waypoints, then applies as in Task 2.
- A **queued** `Move` or `AttackMove`:
  - For a unit with a live order (`OrderSlot ≥ 0` at the settled boundary), append to the book.
  - For an idle unit, apply it immediately as a non-queued order.
- Queued `Hold` and `Stop` are treated as non-queued.
- `WriteBackMovementJob` enqueues `unit.Id` on `Arrivals.AsParallelWriter()` when `Arrived`.
- At the boundary, `SimCommandSystem` drains `Arrivals`, `TryPop`s each id, groups the popped units by `(goal, stance, sizeClass)`, and calls `ApplyOrder` once per group. That way one flow field is shared per group.
- `SimContext.UnitDied` → `Waypoints.Forget(id)`.

```csharp
namespace WAR2D.Sim
{
    /// <summary>
    /// Who attacks whom and who shares vision with whom, per owner slot. Authoritative on the main
    /// thread; copied into SimData.AttackMask / ShareVisionMask at the tick boundary when dirty.
    /// </summary>
    public sealed class Diplomacy
    {
        public ushort AttackMask(int slot);
        public ushort ShareVisionMask(int slot);
        public bool Attacks(int fromSlot, int toSlot);
        public bool SharesVisionWith(int fromSlot, int toSlot);
        public void Join(int slot, int team, IReadOnlyList<(int slot, int team)> others); // starting state from teams
        public void SetAttack(int fromSlot, int toSlot, bool on);
        public void SetShareVision(int fromSlot, int toSlot, bool on);
        public void Leave(int slot);       // clears the slot's row and column
        public bool Dirty { get; }
        public void CopyTo(SimData data);  // writes the masks, clears Dirty; boundary only
    }
}
// SimData gains: NativeArray<ushort> AttackMask, ShareVisionMask (MaxOwners); NativeArray<byte> BuildingOwnerSlot
// SimData loses: Team, BuildingTeam (combat no longer uses teams)
// SimContext gains: public Diplomacy Diplomacy { get; }; SlotOf() calls Diplomacy.Join with TeamOf()
// SimCommandKind gains: SetAttack, SetShareVision; SimCommand gains: public int TargetOwnerId; public bool Flag;
// GameCore (server): [SyncVar] public bool DiplomacyEnabled;   // set from match settings in Task 12; default false
void Cmd_SetAttack(uint targetNetId, bool on, NetworkConnectionToClient sender = null);
void Cmd_SetShareVision(uint targetNetId, bool on, NetworkConnectionToClient sender = null);
[TargetRpc] void ClientPlayer.TargetDiplomacy(NetworkConnection target, ushort attackMask, ushort shareMask, ushort sharedWithMe); // owner's own row only
```

**Rules:**
- **Starting state** (`Join`): for every other slot, same team → neither attacks, both share vision. Different team → both attack, neither shares.
- **Commands** are accepted only when all of these hold:
  - `DiplomacyEnabled`
  - `CurrentState == Playing`
  - the sender is `Playing`
  - the target is another live player
  - the per-sender, per-command cooldown `Diplomacy/ChangeCooldownSeconds` has passed

  They enqueue `SetAttack` or `SetShareVision`, which apply at the boundary.
- **Combat:**
  - `NearestEnemyJob` skips unit `j` unless `(AttackMask[OwnerSlot[i]] >> OwnerSlot[j] & 1) != 0`, and skips building `j` likewise using `BuildingOwnerSlot[j]`.
  - `ResolveTargetsJob` drops a stored target whose owner is no longer attacked.
- **Privacy:**
  - The only message that carries masks is `TargetDiplomacy`, and it carries only the owner's own row, plus `sharedWithMe` (the bits of players who share vision with the receiver).
  - It's sent to the owner on change, and once at match start.
- `GameCore.AreAllies` is deleted (it has no callers). `GameCore.Teams` stays as the public starting teams.

# v0.4 "Legion" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Rebuild the game's core so 10,000 units per player (80,000 per match) run on a player-hosted match within the §4.1 performance budget, using the techniques v0.3 proved.

**Architecture:** The server simulates units as ECS entities in an asynchronous 20 Hz tick: a fixed-rate system group whose Burst jobs run on worker threads between ticks and are settled at the next tick boundary. Pathfinding uses hierarchical flow fields: 32×32-tile sectors with 2×2-tile cells, rebuilt lazily and asynchronously. Combat uses a counting-sort spatial hash and a damage table. Clients receive units through the v0.3 replication encoder: routes plus speed-carrying delta corrections, finer inside the camera view. They draw units with GPU instancing over a generated 1024² map baked into one texture. Players control unlimited box selections and server-side squads.

**Tech Stack:** Unity 6000.4.1f1, Entities 6.4.0, Burst 1.8.28, Collections 2.x, Mathematics, Mirror 96.0.1 + kcp2k, URP 17.4 (2D Renderer), Unity Test Framework 1.6, Unity Performance Testing 3.0.3.

**Spec:** [roadmap design spec](../specs/2026-10-05-war2d-roadmap-design.md): §2 decisions log (including the v0.3 rows), §4.1 budgets, §4.2–§4.5 target architecture, §4.6 spike results, §8 quality process. Also read [roadmap.md](../../roadmap.md) §3 v0.4, [the v0.3 results](../../spike/v0.3-results.md) (every tuning value below comes from there), [architecture.md](../../architecture.md) and [known-issues.md](../../known-issues.md).

**Owner decisions taken before this plan (2026-10-08):**
- **R1. Replication moves into v0.4.** Clients receive units through the spike's encoder (routes, corrections, Enter, Leave, Health) instead of `SyncList`s. Interest is the camera box (own units always, enemies inside the view). v0.5 swaps the camera box for team fog and tunes the transport.
- **R2. The large map is generated from a seed** by the spike's cave generator, with gems and HQ clearings. `Map_2` stays as the small authored map the PlayMode tests use.
- **R3. The map is drawn as one baked texture** (1 texel per tile, point filtered). Real tile art comes in v0.8.

## Global Constraints

- Unity editor **6000.4.1f1**, open on the project, `unity status` = `ready`. Compile with `tools/unity-compile.sh`, test with `tools/unity-test.sh EditMode` and `tools/unity-test.sh PlayMode`. **Both suites must pass at the end of every task.**
- **Performance budget (spec §4.1, as amended by v0.3):**
  - host main-thread server tick **≤ 25 ms p95** at 80,000 units (async tick)
  - client **≥ 60 fps** average with 10,000 own units on screen
  - bandwidth **≤ 256 KB/s average and ≤ 768 KB/s peak (1 s)** per client
  - host upload about 11–16 Mbit/s for 7 remote clients
- **Every gameplay and tuning number lives in `Assets/Resources/GameConfig.xml`**, parsed strictly by `Config.ConfigParser`. No new hard-coded balance values. Spike constants (`SpikeSimRules`) become config values.
- **The server owns the world.** Units and buildings are ECS entities created only on the server. Clients never touch the ECS world.
- **Every `[Command]`:**
  - calls `CommandGate.Allow(sender, nameof(...))` first
  - has a rate budget in `CommandGate`
  - validates every argument server-side, including ownership (`ownerId == BuildingData.UIntToInt(sender.identity.netId)`), game state and ranges
  - is covered by a fuzz test
- **Main-thread code never touches unit entities between ticks.** Commands go through `SimCommandQueue`, which the tick applies at its boundary. A main-thread `EntityManager` call on unit or building archetypes would force the in-flight tick jobs to complete and lose the async budget.
- **Never hand-edit `.unity`, `.prefab` or `.asset` YAML.** Use `unity command ...` (menu items, `run_script`, `eval`) through the live editor. New assets get their `.meta` from the editor.
- **Don't edit vendored code** (`Assets/Mirror/`, `Assets/Plugins/Demigiant/`, `Assets/3rd Party/`). The only exceptions are the deletions of unused vendored files that `known-issues.md` targets at v0.4 (Task 0).
- **Porting from the spike:** spike source is read from the tag with `git show v0.3-spike:Assets/Spike/<path>`. Ported code:
  - drops the `Spike` prefixes and the `WAR2D.Spike` namespace
  - lives in the `WAR2D` assembly under the namespaces this plan names
  - reads config instead of `SpikeSimRules`
  - keeps the spike's XML comments, updated to the new names

  The spike's EditMode tests are ported with the code they cover.
- **Commits:** on `release/v0.4`, one or more per task. **Never** a `Co-Authored-By:` line or any AI attribution (`CLAUDE.md`).
- **Docs:** `architecture.md`, `gameplay.md`, `known-issues.md` and `CLAUDE.md` are updated in the task that changes the behaviour they describe, and finalised in Task 15.

// Gems: rock that faces floor turns to gem with probability gemChance (seeded),
// and every HQ clearing gets a guaranteed 3-tile vein on its rim so a Miner always has a target.
var rng = new Unity.Mathematics.Random(seed * 0x9E3779B9u + 0x7F4A7C15u | 1u);
for (int y = 1; y < size - 1; y++)
for (int x = 1; x < size - 1; x++)
{

    if (tiles[i] != (byte)TileType.Wall) continue;
    bool facesFloor = tiles[i - 1] == 0 || tiles[i + 1] == 0 || tiles[i - size] == 0 || tiles[i + size] == 0;
    if (facesFloor && rng.NextFloat() < gemChance) tiles[i] = (byte)TileType.Gem;
}
foreach (int2 site in hqSites)
{

    for (int k = -1; k <= 1; k++) tiles[(rim.y + k) * size + rim.x] = (byte)TileType.Gem;

{
    public const int MaxIdsPerChunk = 2048, MaxChunkBytes = 8192;
    public static byte[] Encode(IReadOnlyList<int> ascendingIds, int start, int count);  // delta varints
    public static bool TryDecode(byte[] bytes, int maxIds, List<int> into);               // false on any malformed input
}
// Commands (all requiresAuthority = false, NetworkConnectionToClient sender = null, CommandGate first):
void CmdOrderMoveChunk(ushort token, byte[] idChunk, bool final, int2 goal, NetworkConnectionToClient sender = null);

**Server rules:**
- Each sender's chunks are accumulated under `(sender, token)` until `final`.
- Total ids are capped at `MaxUnitsPerPlayer`. A sender can have at most 4 open tokens, and stale tokens are dropped after 2 s.
- Every id is checked to belong to the sender against `SimData` (`IdOf`/`OwnerId` at a settled boundary). Ids that aren't owned or aren't live are silently skipped.
- A move order enqueues `MoveUnits` with the ids, and an assignment replaces the squad.
- `squad` must be in [0, 9] and `goal` inside `MapBounds`; anything else is rejected.
- A player's squads are forgotten when they leave or are eliminated.
- `CmdOrderSquad` orders the squad's living members.

**Client:**
- The left-drag box selects every *own* unit inside it, using `ClientWorld.QueryBox` (no limit). Shift adds to the selection.
- A right click orders the selection: ids are sorted and split into chunks of `MaxIdsPerChunk`, all with the same random token, and the last chunk has `final = true`.
- Ctrl+1–0 assigns the selection to a squad (sent with the same chunking). 1–0 selects the squad from the client's local copy of what it assigned. A right click with a squad selected sends `CmdOrderSquad` when the selection equals that squad exactly, and the chunked move otherwise.

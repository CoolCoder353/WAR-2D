# v0.9 Steam: Design

Status: approved and implemented (merged 2026-10-15). Date: 2026-10-12. Roadmap entry: [roadmap.md](../../roadmap-v0.2-v0.9.md#v09-steam).

## 1. Goal and scope

Make WAR-2D easy to playtest with people on other networks. Today a host needs a router port (UPnP) or a tunnel ([playtesting.md](../../../playtesting.md)); `known-issues.md` lists that as a gap v0.9 closes. v0.9 moves ahead of v0.7 Siege so new content is playtested by more people.

**In scope (the playtest core)**
- Steam relay through the FizzySteamworks transport
- Steam lobbies, invites and a lobby browser
- Authentication tickets, so the server knows each player's Steam ID
- SteamPipe delivery of Linux and Windows builds to a Steam Playtest branch
- Playtest operations (docs, log collection, Windows verification)

**Deferred:** the headless dedicated server; the store page and content survey (including the AI-content disclosure).

**Given (owner, 2026-10-12):**
- The owner has a Steam app ID: **1975300**. The owner wasn't certain of the number, so phase 0 confirms it in the Steamworks dashboard before it goes into `steam_appid.txt` or the upload scripts.
- No store page is needed for the playtest.

## 2. Approach

Steam first, KCP kept as "Direct". Mirror's `MultiplexTransport` carries FizzySteamworks and KCP. The Join screen lists Steam lobbies and keeps a small "Direct (IP)" field. Tests, perf and QA keep using KCP and never need the Steam client.

Rejected: Steam only (breaks the perf, QA and test harnesses); invite-only relay with no browser (weak for finding a game).

## 3. Design

### 3.1 Connection layer
`GameManager.HostServer()` and `ConnectToServer(address)` are the only entry points into networking. A small `ConnectionRoute` (a Steam ID, or an address and port) sits behind them. Nothing past connect changes: the sim, replication, fog and `CommandGate` identify players by Mirror `netId`.

`HostReachability` / UPnP stays, but only runs for a Direct host.

### 3.2 Lobbies
- The host creates a Steam lobby (max 8) with metadata: map, mode, game version, state.
- Players browse the lobby list or accept an invite; the lobby gives the client the host's Steam ID, and the client connects to it over the relay.
- The lobby closes to new joins when the match starts (the same rule as `LobbyRules.MayJoin`). Rich presence shows the lobby or match state in the friends list.
- The lobby UI is a HUD/menu change, so it goes through Figma first and needs the owner's approval before it is built.

### 3.3 Identity
A Mirror `Authenticator` verifies Steam auth tickets (`GetAuthSessionTicket` on the client, `BeginAuthSession` on the host). It also checks the game version and refuses mismatched builds.
- The Steam ID is stored on `ServerPlayer` (server-side only; it never goes to other clients unless a later feature needs names).
- Nicknames default to the Steam persona name and still pass the existing sanitiser.
- `CommandGate` rate-limit and kick decisions can key on the Steam ID.
- Direct connections skip Steam auth and are allowed only when the host opted in (dev and LAN).

### 3.4 Isolation from tests
Steam code lives in its own assembly behind a scripting define. EditMode and PlayMode tests build without it; the Steam path gets its own tests against a fake `ISteamBackend` (lobby creation, ticket validation, version refusal).

### 3.5 Vendored code
Steamworks.NET and FizzySteamworks go in `Assets/3rd Party/` and are not edited. Custom code wraps them.

### 3.6 Delivery
`tools/steam-upload.sh` drives `steamcmd` with checked-in depot and build scripts: one depot per OS (Linux, Windows), uploaded to a Playtest branch. A build number and the game version string are shared with the lobby metadata so that mismatches are caught early.

Both test suites run once per commit, per the project rule, not after every edit.

## 5. Risks

- **Throughput over the relay.** Steam's networking has message-size and rate limits. Replication messages are chunked already, but this is unmeasured: phase 5 is a hard gate, and phase 1 logs the largest message sent.
- **Windows is unverified.** `Builds/Windows` exists but has not been played. Phase 6 and 7 verify it.
- **Linux Steam runtime.** The Linux build must run under Steam's runtime. Checked in phase 6.
- **Playtest app structure.** Steam Playtest may use a separate app ID from the main app. Phase 0 confirms that 1975300 is the ID the build, the lobby and `steam_appid.txt` should use.
- **Unverified Steam requirements** beyond the store page are checked against Valve's documentation in phase 0, not assumed.

## 6. Out of scope
Dedicated server, store page and content survey, matchmaking, achievements, cloud saves, Steam Input, and anything for v0.7.
